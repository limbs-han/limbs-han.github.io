8.8GB 원본 덤프

실제 문서 521,633개

Spark로 원본을 읽고 다른 문서로 연결만 하는 항목을 제외했습니다. 추천에 쓸 문서 관계는 미리 계산해 필요한 파일만 받도록 나눴습니다.

링크 19,015,524개 / 배포 파일 1,024개 / 압축 합계 154.3MB

추천 데이터를 만드는 곳과 사용하는 곳

  1. PC에서 덤프 가공

    Spark로 문서를 읽고 정제 / 링크 해석률 95.6%

  2. PC에서 추천 이웃 계산

    문서 내용을 숫자로 바꾼 임베딩과 문서 분류를 함께 사용

  3. GitHub Pages에 배포

    추천 데이터를 정적 파일로 나눠 공개

  4. 브라우저에서 개인화

    IndexedDB에 저장한 열람 기록으로 추천

핵심 판단

추천은 미리 계산하고, 개인화는 브라우저에 남겼습니다.

열람 기록을 서버에 모으는 구조는 개인정보 처리와 운영 부담이 컸습니다. 개인화는 브라우저에 남기고 추천 관계는 미리 계산해 파일로 배포하기로 했습니다.

8.8GB 처리 중 메모리 부족으로 멈췄을 때는 Spark 드라이버 메모리를 8GB에서 10GB로 늘리고, 파티션 크기를 128MB에서 64MB로 줄여 처리했습니다.

서버를 두지 않는 대신 새 문서 대응과 사용자 로그를 통한 추천 품질 측정은 남았습니다.

게시 후 바꾼 조건

잠깐 열어 본 문서까지 다른 문서를 추천하는 근거로 쓰였습니다. 그래서 누적 체류 시간이 30초 미만인 문서는 추천의 근거에서 제외했습니다. 열람 기록은 남겨 두므로, 다시 읽어 누적 30초를 채우면 근거로 쓸 수 있습니다. 30초는 초기 기준이며 추천 품질의 측정값은 아닙니다.

핵심 판단

같은 가공 구간을 비교하도록 시작점을 맞췄습니다.

가공 사이클마다 시작점이 달라, 같은 순서의 값을 놓고도 서로 다른 가공 구간을 비교하게 될 수 있었습니다. 그래서 부하값이 올라가는 시점을 기준으로 시작점을 맞추자고 제안했습니다.

실제 전처리에서는 부하값과 직전 값의 변화를 보고 앞부분을 자른 뒤 시작 시각을 0으로 설정했습니다. 선형보간과 입력 길이 조정으로 비교 기준을 맞췄습니다.

실제 불량을 표시한 데이터가 부족해 정상 패턴을 학습하는 방법을 검토했습니다. 팀은 LSTM과 비교한 뒤 정밀도와 재현율의 균형을 고려해 GAN을 선택했습니다.

실제 정상 데이터와 GAN이 생성한 정상 데이터를 합쳐 가공 시점별 정상 범위를 만들고, 범위 이탈을 기준으로 이상을 판단했습니다.
