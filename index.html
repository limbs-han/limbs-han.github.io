한눈

정제 기사

1,115만 건

기존 데이터셋 1,002만 건에 비어 있던 20개월치는 빅카인즈에서 채웠습니다. 빅카인즈 본문은 200자에서 잘려 기사 주소만 받고 본문은 직접 다시 추출해 145만 건을 더했고, 13개 언론사 실시간 수집분과 함께 기사당 1행의 공통 스키마로 합쳐 15분마다 갱신했습니다.

핵심 판단

중복 이슈 번호 교정

상황

13개 언론사 기사를 사건별 이슈로 묶어 백엔드에 발행했는데, 같은 사건이 화면에 여러 이슈로 나왔습니다.

문제

9월 7일부터 20일까지 이슈 번호를 이어받은 비율은 73.4%였고, 명백히 놓친 경우가 742건이었습니다. 날짜가 바뀌면 같은 사건에도 새 번호가 붙는 구조였습니다.

행동

분석 단계를 고치는 방법, 저장된 Gold를 고치는 방법, 발행 직전에 바로잡는 방법을 비교해 발행 직전 교정을 골랐습니다. 각 단계의 담당 범위와 분석 결과 기록은 그대로 두고, 밖으로 나가는 데이터만 바로잡기 위해서입니다.

발행 직전에 최근 3일 이슈와 비교해 같은 사건이면 기존 번호를 쓰게 했고, 같은 사건으로 보는 기준은 분석 단계와 똑같이 맞춰 이슈의 계보가 갈리지 않게 했습니다. 대신 분석 단계의 규칙이 바뀌면 발행 쪽도 함께 바꿔야 하는 부담이 남아, 번호 부여 방식 개선은 과제로 공유했습니다.

결과

첫 실행에서 374개 중 81개를 기존 번호로 이었습니다.

운영 중 저장 형식 전환 날짜 2,814개 건수 불일치 0

15분마다 기사가 들어오는 파이프라인을 멈추지 않고 정제 데이터를 Parquet에서 Iceberg로 옮겼습니다. 전환 뒤에는 바뀐 날짜를 폴더 탐색 대신 테이블 파일 목록으로 찾게 되어, 분석팀 입력 추출이 46.6초에서 20.1초로 줄었습니다.

Spark 쓰기 파일 정리 커밋 30분 → 6초

중복 제거는 article_id로 데이터를 나누고 저장은 날짜별로 해서, 나뉜 조각마다 날짜별 파일이 생겨 날짜 2,800개에 파일 545,600개가 쌓였습니다. 쓰기 직전에 repartition("dt")로 날짜 기준으로 다시 나눠 날짜당 파일 1개로 만들었습니다.

핵심 판단

악보 인식 정확도 개선

상황

악보 PDF를 채점용 데이터로 바꾸기 위해 공개 악보 인식 모델을 썼습니다. 단소 실기교재 5곡을 읽자 율명 정확도는 63%였습니다.

문제

틀린 유형을 나눠 보니 옥타브 오류가 가장 많았고, 모델이 아는 글자 142개 중 중청 계열은 하나뿐이었습니다. 재학습으로 풀려면 교재 자료를 학습에 써도 되는지, 평가 곡 분리, GPU와 배포까지 함께 정해야 했습니다.

행동

재학습은 별도 과제로 남기고 인식 뒤 후처리로 고쳤습니다. 악기 음역으로 후보를 줄인 뒤 글자 모양으로 옥타브만 다시 고르게 했습니다.

곡별 율명 목록으로 제한하는 방법은 73%까지 올랐지만, 정답에서 뽑은 목록이라 실제보다 유리하게 재는 방식이어서 비교에서 뺐습니다. 칸 모양 일치가 100/120에서 97/120으로 조금 낮아지는 것은 감수했고, 80%에서 멈춰 사람이 인식 결과를 고치는 운영을 전제로 했습니다.

결과

옥타브 오류가 44개에서 6개로 줄었고, 곡 하나씩 빼고 검증해도 95%(75/79)를 유지했습니다.

악보 인식 서버 8곡 중 7곡 실패 → 8곡 일치

PDF 글자 층, 스캔본, 오선보는 각각 다른 엔진으로 읽되, 모두 정간보 중간 형식을 거쳐 같은 공통 악보 변환기로 들어가게 해 어느 경로로 들어와도 같은 형식이 나오게 했습니다. 기존 도구가 실패하던 글자 층 정간보는 가려진 긴 선, 여러 단 판형, 겹친 글자를 처리해 1쪽 1.0초에 읽습니다.

공통 악보 변환기 불변식 6종 검사

박은 분수로 계산한 뒤 모든 분모의 최소공배수를 단위로 한 정수 틱으로 저장해 부동소수 오차를 없앴습니다. 음표 ID는 c{각}-j{정간}처럼 위치로 만들어 같은 입력이면 같은 ID가 나오게 했고, 이 ID로 운영 악보와 음표 단위 대조가 가능해졌습니다. 길이 합, 빈틈과 겹침, 참조, 율명, 개수, 두 번 변환한 결과의 바이트 일치 중 하나라도 어기면 결과 파일을 쓰지 않습니다.

채점 박자 판정 개선 평균 54점 → 83점

pYIN 음높이 추정과 DTW 정렬로 채점 엔진을 설계했습니다. 박자를 곡 처음부터 계산해 조금씩 느려지는 정상 연주까지 틀린 것으로 판정했고, 앞뒤 3음을 기준으로 판정하도록 바꿨습니다. 실제 입문자 녹음으로 잰 결과입니다.

핵심 판단

추천 데이터 정적 배포

상황

서버 없이 52만 문서의 추천 관계를 미리 계산해 GitHub Pages로 배포하는 구조였습니다.

문제

GitHub Pages에는 사이트 1GB, 월 대역폭 100GB 한도가 있고, 브라우저는 문서 하나를 볼 때 필요한 조각만 받아야 했습니다. 이웃 계산량도 CPU로 9~30일이 걸리는 규모였습니다.

행동

크기 기준을 전체 500MB, 파일 하나 1MB로 먼저 정하고 추천 결과를 1,024개 파일로 나눴습니다. 이웃 계산은 GPU 전수 탐색으로 바꿔 6분에 끝냈습니다.

새 문서를 바로 추천하지 못하고, 사용 지표가 없어 추천 품질을 잴 수 없으며, 사용자가 수천 명 규모가 되면 대역폭 한도를 다시 봐야 하는 점은 감수했습니다.

결과

전체 154.3MB, 파일 하나 최대 0.176MB로 배포했고, 2주 만에 크롬 웹스토어 첫 제출을 통과했습니다.
