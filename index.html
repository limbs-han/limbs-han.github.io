한눈

13개 언론사의 뉴스를 사건별로 묶고 관점을 비교하는 서비스

분석팀에 보낼 데이터 추출 시간

20.1초

전환 전 46.6초 → 56.9% 단축

핵심 판단

새 기사가 쌓여, 저장소를 바꾸기 직전에 다시 대조했습니다.

분석팀에 보낼 데이터를 만들 때 날짜 폴더 2,814개의 수정 시각을 확인했습니다. Iceberg로 읽기를 바꾸면서도 분석팀의 JSONL 입력과 새 기사 전달은 유지해야 했습니다.

폴더 시각 대신 테이블의 파일 목록과 행 수로 변경을 판단했습니다. 재구축 뒤에도 사흘간 새 기사가 들어왔으므로, 배치를 멈추고 두 저장소를 다시 대조한 뒤 읽기를 전환했습니다.

중복 이슈 대응

같은 사건에 새 번호가 붙어 서비스에 중복으로 보였습니다. 13일치 기록에서 이 문제를 찾은 뒤, 새 이슈를 내보내기 직전에 최근 3일 동안 발행한 이슈와 비교해 같은 사건이면 기존 번호를 쓰도록 했습니다. 첫 실행에서는 374개 중 81개를 기존 번호로 연결했고, 품질 지표 5개도 추가했습니다. 기사 분석 쪽 원인은 담당 팀원에게 넘겼습니다.

담당 경계와 전달

수집과 적재는 15분 주기, Spark는 단일 서버 local 모드입니다. Kafka 서버와 기사 분석은 팀원 담당입니다. 분석팀에 보내는 데이터 형식과 복구 절차를 문서로 남겼습니다.

핵심 판단

카드마다 다른 조건을 하나의 기본값으로 처리하지 않았습니다.

할부 실적과 결제 취소 처리도 카드마다 달랐습니다. 계산 방식에 담지 못하는 조건은 미지원으로 남기고, 형식이 맞는 초안과 실제 계산에 쓸 규칙을 분리했습니다.

원문이 바뀐 카드만 다시 추출했습니다. 검수를 통과한 카드 규칙을 카탈로그로 내보내고, GitHub를 거쳐 앱에 반영했습니다.

원문 조사와 기대값 검증을 구현과 나눠, 통과 여부뿐 아니라 원문과 계산 근거를 확인했습니다.

원문 → 추출 초안 → 대조와 승인

실제 Databricks의 초안 테이블과 승인 테이블

수집 실패를 분리해 95.0% → 99.3%

PDF를 읽다가 오류가 나면 수집 작업도 함께 멈췄습니다. 그래서 PDF 해석을 별도 프로세스로 옮겨, 한 문서에서 오류가 나도 다음 수집을 이어가게 했습니다. 재수집 뒤 대상 1,846장 중 원문 확보가 1,754장 → 1,834장으로 늘었습니다.

명세서 대조 187건 중 170건 일치

초기 Python 엔진을 5달치 명세서와 대조했습니다. 남은 17건은 조건 9건, 명세서 밖 혜택 5건, 이전 이력 2건, 혜택 구분 불가 1건으로 나눠 남겼습니다.

03 / 개인 프로젝트

namu-reco

읽은 나무위키 문서로 다음 문서를 추천하는 크롬 확장 프로그램

기간
2026.08 ~ 2026.09 / 첫 게시 이후 개선 포함
역할
기획, 개인정보 경계와 배포 구조 선택, 검증. AI 도구로 구현
기술
Python, PySpark, 문서 임베딩, IndexedDB, Chrome Extension

8.8GB 덤프에서 가공한 문서

약 52만 개

521,633개 문서 / 19,015,524개 링크

1,024개 파일, 압축 합계 154.3MB 배포
핵심 판단

혼자 운영할 수 있는 범위를 먼저 정했습니다.

열람 기록을 서버에 모으는 구조는 개인정보 처리와 운영 부담이 컸습니다. 개인화는 브라우저에 남기고 추천 관계는 미리 계산해 파일로 배포하기로 했습니다.

8.8GB 처리 중 메모리 부족으로 멈췄을 때는 Spark 드라이버 메모리를 8GB에서 10GB로 늘리고, 파티션 크기를 128MB에서 64MB로 줄여 처리했습니다. 첫 버전은 2주 안에 완성해 스토어에 제출했습니다.

서버를 두지 않는 대신 새 문서 대응과 사용자 로그를 통한 추천 품질 측정은 남았습니다.

계산은 PC에서, 개인화는 브라우저에서

  1. 01
    공식 덤프 8.8GB파싱과 정제 / 링크 해석률 95.6%
  2. 02
    문서별 추천 관계 계산미리 계산한 이웃 데이터
  3. 03
    GitHub Pages 파일 배포1,024개 파일 / 필요한 파일만 읽기
  4. 04
    IndexedDB에서 개인화열람 기록은 브라우저에 보관

게시 후 바꾼 조건

잠깐 열어 본 문서까지 다른 문서를 추천하는 근거로 쓰였습니다. 그래서 누적 체류 시간이 30초 미만인 문서는 추천의 근거에서 제외했습니다. 열람 기록은 남겨 두므로, 다시 읽어 누적 30초를 채우면 근거로 쓸 수 있습니다. 30초는 초기 기준이며 추천 품질의 측정값은 아닙니다.

04 / 기업 연계 졸업 프로젝트

GAN 기반 CNC 이상탐지

CNC 가공 설비의 부하 패턴에서 이상을 찾는 다빈소프트 연계 프로젝트

기간
2025.04 ~ 2025.06 / 4인 팀
역할

기술

핵심 판단

같은 순서의 값이 같은 가공 구간을 뜻해야 했습니다.

가공 사이클마다 시작점이 달라, 같은 순서의 값을 놓고도 서로 다른 가공 구간을 비교하게 될 수 있었습니다. 그래서 부하값이 올라가는 시점을 기준으로 시작점을 맞추자고 제안했습니다.

실제 전처리에서는 부하값과 직전 값의 변화를 보고 앞부분을 자른 뒤 시작 시각을 0으로 설정했습니다. 선형보간과 입력 길이 조정으로 비교 기준을 맞췄습니다.

실제 정상 데이터와 GAN이 생성한 정상 데이터를 합쳐 가공 시점별 정상 범위를 만들고, 범위 이탈을 기준으로 이상을 판단했습니다.

별도 모델 시험 / 팀 최종 결과

초기 정상 사이클 일부로 학습하고, 실제 불량 정답이 부족해 테스트 데이터의 5%에 이상을 주입했습니다.
