정제 기사

1,115만 건

기존 데이터셋 1,002만 건에 비어 있던 20개월치는 빅카인즈에서 채웠습니다.
빅카인즈 본문은 200자에서 잘려, 기사 주소만 받고 본문은 직접 다시 추출해 145만 건을 더했습니다.
여기에 13개 언론사 실시간 수집분을 합쳐 기사당 1행의 공통 스키마로 15분마다 갱신했습니다.

핵심 판단

중복 이슈 번호 교정

상황

분석 단계는 하루 단위로 기사를 사건별로 묶어 이슈 번호를 붙이고, 전날과 같은 사건이면 전날 번호를 이어받게 되어 있었습니다.
데이터 파이프라인은 이 이슈를 번호 기준으로 백엔드에 발행했는데, 같은 사건이 화면에 여러 이슈로 나왔습니다.

문제

원인을 찾아보니, 날짜가 바뀐 첫 실행에서 이어받기가 실패하면 그날 남은 실행이 그 번호를 그대로 따라갔습니다.
실제로 9월 7일부터 20일까지 이어받아야 할 이슈 중 73.4%만 이어받았고, 명백히 놓친 경우가 742건, 하루 평균 57건이었습니다.
그런데도 작업은 모두 성공으로 끝나 어떤 실패 지표에도 잡히지 않았습니다.

행동

고칠 수 있는 곳은 분석 코드, 이미 저장된 이슈 결과인 Gold, 백엔드로 내보내기 직전의 세 곳이었습니다.
분석 코드와 Gold는 건드리지 않고 내보내기 직전에서 바로잡았습니다.
분석 코드는 분석 담당의 영역이고, Gold는 분석 결과의 원본 기록이기 때문입니다.

내보내기 직전에서는, 오늘 이슈의 기사 중 2건 이상이자 과반이 최근 3일 안에 발행된 한 이슈에 있으면 그 번호를 쓰게 했습니다.
대신 분석 단계의 번호 규칙이 바뀌면 이 교정도 함께 바꿔야 해서, 측정 결과와 재현 자료를 분석 담당에게 넘겼습니다.

결과

첫 실행에서 새 번호로 나갈 뻔한 이슈 81개를 기존 번호로 이었습니다.

운영 중 저장 형식 전환 날짜 2,814개 건수 불일치 0

15분마다 기사가 들어오는 파이프라인을 멈추지 않고 정제 데이터를 Parquet에서 Iceberg로 옮겼습니다. 전환 뒤에는 바뀐 날짜를 폴더 탐색 대신 테이블 파일 목록으로 찾게 되어, 분석팀 입력 추출이 46.6초에서 20.1초로 줄었습니다.

Spark 쓰기 파일 정리 커밋 30분 → 6초

중복 제거는 article_id로 데이터를 나누고 저장은 날짜별로 해서, 나뉜 조각마다 날짜별 파일이 생겨 날짜 2,800개에 파일 545,600개가 쌓였습니다. 쓰기 직전에 repartition("dt")로 날짜 기준으로 다시 나눠 날짜당 파일 1개로 만들었습니다.

핵심 판단

악보 인식 정확도 개선

상황

악보 PDF를 채점용 데이터로 바꾸려고 공개 악보 인식 모델을 썼는데, 단소 실기교재 5곡의 율명 정확도가 63%였습니다.

문제

틀린 유형을 나눠 보니 옥타브 오류가 가장 많았습니다.
모델이 낼 수 있는 글자 142개 중 중청 계열이 하나뿐이라, 처음부터 맞힐 수 없는 글자가 있었기 때문입니다.

행동

그래서 먼저 단소가 낼 수 없는 음을 인식 후보에서 뺐습니다.
그다음 모델이 높은 음으로 읽은 자리는 정답 글자들의 평균 모양과 비교해 옥타브만 다시 골랐습니다.

정답에서 뽑은 곡별 율명 목록으로 후보를 줄이면 73%까지 올랐지만, 실제보다 유리하게 재는 방식이라 뺐습니다.
고른 방법은 칸을 나눈 모양을 맞힌 수가 120칸 중 100칸에서 97칸으로 줄었지만, 이는 감수했습니다.
정확도는 80%에서 멈추고, 남은 오류는 사람이 고치는 운영을 전제로 했습니다.

결과

옥타브 오류가 44개에서 6개로 줄었습니다.
또 한 곡씩 빼고 만든 평균 모양으로 다시 재도 옥타브를 고른 79자 중 75자, 95%가 맞았습니다.

악보 인식 서버 8곡 중 7곡 실패 → 8곡 일치

PDF 글자 층, 스캔본, 오선보는 각각 다른 엔진으로 읽되, 모두 정간보 중간 형식을 거쳐 같은 공통 악보 변환기로 들어가게 해 어느 경로로 들어와도 같은 형식이 나오게 했습니다. 기존 도구가 실패하던 글자 층 정간보는 가려진 긴 선, 여러 단 판형, 겹친 글자를 처리해 1쪽 1.0초에 읽습니다.

공통 악보 변환기 불변식 6종 검사

박은 분수로 계산한 뒤 모든 분모의 최소공배수를 단위로 한 정수 틱으로 저장해 부동소수 오차를 없앴습니다. 음표 ID는 c{각}-j{정간}처럼 위치로 만들어 같은 입력이면 같은 ID가 나오게 했고, 이 ID로 운영 악보와 음표 단위 대조가 가능해졌습니다. 길이 합, 빈틈과 겹침, 참조, 율명, 개수, 두 번 변환한 결과의 바이트 일치 중 하나라도 어기면 결과 파일을 쓰지 않습니다.

채점 박자 판정 개선 평균 54점 → 83점

pYIN 음높이 추정과 DTW 정렬로 채점 엔진을 설계했습니다. 박자를 곡 처음부터 계산해 조금씩 느려지는 정상 연주까지 틀린 것으로 판정했고, 앞뒤 3음을 기준으로 판정하도록 바꿨습니다. 실제 입문자 녹음으로 잰 결과입니다.

카드사 약관이 바뀌면 카드 혜택 규칙을 고쳐 승인했습니다.
그런데 승인 작업의 MERGE는 맞지 않는 옛 행을 지우고 새 행을 넣어서, 승인된 규칙 표에는 카드마다 지금 규칙만 남았습니다.

문제

그래서 앱이 지난달 어떤 규칙으로 혜택을 계산했는지 나중에 확인할 수 없었습니다.
표의 변경 기록을 받아 이력을 따로 쌓으려 해도, 지우기와 넣기 중 무엇을 먼저 처리할지 정할 수 없었습니다.
승인 한 번이 같은 규칙에 옛 행 지우기와 새 행 넣기를 같은 버전 번호로 남겼기 때문입니다.

행동

승인 쓰기 방식은 그대로 두고, 변경 데이터 피드를 AUTO CDC로 받아 SCD2 이력 표를 만들었습니다.
이때 순서 값에 버전 안의 차례를 더해, 지우기가 먼저 옛 행을 닫고 넣기가 새 행을 열게 했습니다.
변경 기록은 기본 보존 기간이 지나면 표 정리 작업이 지웁니다.
그래서 이력 작업이 한동안 멈춰도 읽을 수 있게 보존 기간을 60일로 늘렸습니다.

대신 이력이 한 시간에 한 번까지만 반영되는 점과, 승인 표에 옛 행이 남지 않아 이력 표를 처음부터 다시 쌓을 수 없다는 점은 감수했습니다.

결과

운영 중인 카드 규칙 22개를 이력 표에 처음 적재했습니다.

대신 새 문서를 바로 추천하지 못하고 사용 지표가 없어 추천 품질을 잴 수 없는 점은 감수했습니다.
사용자가 수천 명 규모가 되면 대역폭 한도도 다시 봐야 합니다.

핵심 판단

GAN 기반 정상 범위 생성

상황

기업이 준 CNC 설비 데이터는 정상 가공 기록뿐이라, 이상 사례도 정상과 이상을 구분한 레이블도 없었습니다.

문제

그래서 지도학습은 처음부터 쓸 수 없었고, 정상 데이터만으로 판정 기준을 세워야 했습니다.
그런데 가공 도중에 이상을 잡으려면 다 쌓이기 전에 판단해야 해서, 정상 데이터도 처음 29개 사이클뿐이었습니다.

행동

설비 이상은 놓치는 비용이 잘못 울리는 비용보다 크다고 보고, 재현율을 우선 지표로 정했습니다.
LSTM으로 판정하는 방식도 재현율은 90% 넘게 올렸지만, 정밀도와의 균형은 GAN 쪽이 나았습니다.
그래서 GAN으로 정상 사이클 5,000개를 만들어 실제 29개와 합친 범위로 판정하는 쪽을 골랐습니다.
생성한 사이클이 실제와 비슷한지는 그래프로만 비교해, 정량 검증이 부족한 점은 감수했습니다.

결과

범위를 벗어난 지점이 3개 이상 쌓이면 이상으로 판정했습니다.
테스트 사이클의 5%에 이상을 넣은 시험에서 재현율 100%, F1 점수 76.92%를 얻었습니다.
